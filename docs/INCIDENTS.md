## Incident history

### 2026-09-09: worker.js corruption (PRs #3, #4)

Two PRs, both titled *"Update print statement from 'Hello' to 'Goodbye'"* with no description, were merged directly to `main`. Despite the placeholder titles, they replaced the hand-written `worker.js` source with esbuild-bundled output, committed twice (`__name()`/`__defProp()` bundler artifacts, comments stripped, every function declared twice back-to-back). Because JS lets a later top-level `function` declaration silently shadow an earlier one, only the *second* copy of each function actually ran — this included a digest-email header-border fix that looked shipped but was actually dead code the whole time.

No malicious intent was found in the diff (no new external domains, no credential exfiltration, no eval/backdoor patterns) — this reads as an accidental bundle-output-committed-as-source mistake, twice, under a badly mismatched placeholder commit message, not a compromise. But it went straight to `main` and would have auto-deployed live with zero review gate, which is the actual systemic issue (see "Deploy process" — the sanity-check step exists because of this).

**Fixed in PR #5** (merged 2026-09-10): rebuilt `worker.js` from the last known-good commit (`806090f`) and manually ported forward the legitimate feature work that had been buried in the duplicate (the `/api/star-show` My Shows email feature).

If a commit/PR title doesn't match its diff size, or an empty PR body sits on a substantial change, treat it the way this one should have been treated: stop, diff it against the last known-good state, and don't build on top of it until the actual change is understood.

### The Wednesday-3pm-digest mystery, 2026-09-17 — root cause never actually found, but ruled out what it wasn't

A subscriber-facing digest fired Wednesday 2026-09-16 at exactly 3:00 PM ET — the *exact* old pre-2026-09-12 schedule, both day and time, to the exact expected subscriber list. Investigated at length:
- **Not a stale/duplicate Cloudflare Cron Trigger.** Both deploys since the Thu-1pm-ET schedule change (`wrangler deploy`'s own logged output for PR #67 *and* PR #68, the last deploy in that day's sequence) explicitly printed `schedule: 0 17 * * thu` as the trigger Cloudflare's API accepted. The live dashboard's Triggers panel agreed (Thursday, count of 1).
- **But it did fire via the real Cron Trigger, not a manual/external call.** Workers Observability logs (the per-Worker "Logs" tab, not the bindings/architecture Overview page) showed a `show-tracker-api scheduled OK` entry at exactly 2026-09-16 15:00:36 EDT — `scheduled` is the log type Cloudflare only emits for an actual Cron Trigger invocation calling the `scheduled()` handler; nothing else in this codebase reaches that code path.

### Digest engagement showing zero opens investigated, 2026-09-17 (not a bug — client-side)

User reported the admin panel's digest engagement stats showed zero opens despite genuinely opening that week's email, and asked whether their VPN + Safari Private Browsing use could be the cause. Investigation:
- **VPN/Private Browsing are unlikely culprits.** A VPN only changes IP, doesn't block image loads. Safari's tracking prevention targets cookie-based cross-site tracking, not a plain `<img>` GET. Apple Mail's "Protect Mail Activity" (Mail Privacy Protection) — a different, Mail-app-specific feature — actually *inflates* opens toward 100% via proxy pre-fetching, the opposite of suppressing them.
- **User checked Resend's own per-email Insights panel directly** (screenshot) for the specific digest send: the delivery timeline stopped at "Delivered," no "Opened" step at all, while "Use custom subdomain for open/click tracking" both showed green/"Doing great" — confirming tracking *is* enabled and properly configured at the account level. This ruled out both a Resend-config problem and a webhook problem: Resend itself never saw the tracking pixel requested, so our webhook was never going to fire regardless of its own health.
- **Conclusion: the reader's mail client never loaded the remote tracking-pixel image** for that specific open — most likely "load remote images" wasn't enabled/triggered in whatever client was used. Not fixable from this codebase.
- **Added general-purpose webhook health diagnostics anyway (PR #90)**, since the two failure modes ("nothing's arriving" vs. "everything's being rejected") otherwise look identical (both show all-zero counters) and this was worth being able to rule out quickly next time without a per-email Resend dashboard lookup. `handleResendWebhook` now records the most recent webhook call of *any* type (timestamp, event type, signature status) to a single KV key, plus a per-day signature-failure counter (reuses `digestStatsWindow`'s `digest-stats:{type}:{date}` bucketing under `type: 'sigfail'`). Admin panel shows it in red when something looks wrong: secret not configured, no call ever received, recent signature failures, or nothing in over ~10 days (longer than the weekly cadence). This cannot see or explain an individual reader's pixel-loading behavior — that stays Resend-Insights-only, per-email.

### charlestonlivemusic.com timezone-mislabeling bug found and fixed, 2026-09-17 (post-PR #91)

User caught two Refinery times as wrong after PR #91 merged: Dani Rucker (stored `sh: 4:00 PM`, actually doors 7:00 PM / show 8:00 PM) and Trampled by Turtles (stored `dr: 3:30 PM` — a "doors time" PR #91 itself had invented — actually doors 6:00 PM, show correctly already 7:30 PM). Root-caused by fetching the raw JSON-LD directly (`curl` + regex on the actual event pages, not WebFetch's markdown conversion, which the PR #91 research pass had already noted "hallucinates" times from boilerplate text):

- **The actual bug:** charlestonlivemusic.com's schema.org `startDate`/`endDate` fields are the venue's real Eastern wall-clock time, but the site's own schema generator tags them with a literal `+00:00` (UTC) suffix instead of the correct `-04:00`/`-05:00` offset — e.g. Trampled by Turtles' real 7:30 PM show is emitted as `"startDate":"2026-10-16T19:30:00+00:00"`. Converting that "UTC" value to Eastern (correctly, by our own conversion logic — subtracting 4 hours for EDT) takes an already-correct local time and shifts it 4 hours too early, producing a plausible-looking but fabricated time. Confirmed the same pattern on Ashley McBryde and Judah & The Lion (both `19:30:00+00:00` → real 7:30 PM show, not a `dr` value).
- **A second, separate problem on the same source:** several Refinery "Limbo" showcase event pages (Dani Rucker, Caleb Lee Hutchinson, Jesse Roper) return `"startDate":"1970-01-01T00:00:00+00:00"` — the Unix epoch, i.e. no real date was ever entered in the site's CMS for these events — not a timezone artifact at all, just a placeholder with the shape of a real timestamp. PR #91's research pass (and, it turns out, an earlier 2026-09-01 session for Dani Rucker) treated these as legitimate data and, worse, used one bad value (Dani Rucker's fabricated 4:00 PM) as a "confirmed" calibration point to justify inferring a fake "doors is always ~4 hours before show" rule, which is how the incorrect Trampled by Turtles/Ashley McBryde/Judah & The Lion/Beartooth `dr` values got introduced in the first place. **A stored value is not ground truth just because an earlier session recorded it with confidence** — re-derive from the primary source when validating a new inference, don't chain trust through a value nobody has re-verified.
- **Checked whether this is systemic:** verified Tin Roof's tockify ICS feed (`DTSTART:20260902T230000Z` for Sheer Terror, converts correctly to the doors time — 7:00 PM — stated in the feed's own `SUMMARY` text) and livemusiccharleston.com's `/api/events/global` (`"start":"2026-09-20T21:00:00Z"` for a Uptown Social FlashMob show, converts correctly to the already-confirmed 5:00 PM). Both are genuinely, correctly-labeled UTC — **this bug is isolated to charlestonlivemusic.com specifically**, not a problem with this routine's UTC-conversion logic in general.
- **Fixed:** Dani Rucker (`sh: 8:00 PM`, `dr: 7:00 PM`, per user), Trampled by Turtles (`dr: 6:00 PM`, per user). Reverted the three other fabricated `dr` values from PR #91 (Ashley McBryde, Beartooth back to `"see ticket link"`; Judah & The Lion's `dr` reverted but its `sh` genuinely gained `7:30 PM`, since that reading — literal local time, ignoring the false UTC tag — matches the validated McBryde/Trampled-by-Turtles pattern). Reverted Jed Harrelson and Jesse Roper's `sh` fills from PR #91 back to `"see ticket link"` (both were copied from the debunked Dani Rucker/Caleb Lee Hutchinson calibration, not independently sourced). Left Caleb Lee Hutchinson's pre-existing `sh: 3:00 PM` value as-is (out of scope, predates this session) but added a `flag` — same epoch-zero JSON-LD, same suspicion, needs independent confirmation, not silently corrected without one.
- **Corrected routine instruction for The Refinery's fetch strategy, replacing the "use charlestonlivemusic.com JSON-LD `startDate` for times" guidance:** before trusting any `startDate`/`endDate` value from this source, fetch the raw JSON-LD directly (curl, not WebFetch) and check it isn't `1970-01-01T00:00:00` (placeholder/no real date — if so, treat the event as having no time data from this source at all, leave `sh`/`dr` as `"see ticket link"`). If it's a real date, read the date/time digits literally as America/New_York local time — **do not** apply a UTC→Eastern conversion to it, despite the `+00:00` suffix, since that suffix is wrong on this site. Never infer a "doors time" from this field; a real (non-epoch) value here has only ever been observed to equal the actual show start time, never doors — if doors time is needed and not stated elsewhere, leave it unconfirmed rather than guess an offset. And never use another session's previously-stored value as independent confirmation of a new inference technique — re-derive from the primary source.
